Proposed scope and portable schema v1 (contract to reconcile with existing owners)
- Server derives realm/account/current character from authenticated identity and
  verifies ownership on EVERY list/read/create/restore request. Names are labels.
- Account templates: explicitly selected portable general preferences and layout
  presets. Per-character snapshots: macros, job action assignments, per-character
  retail settings and existing layout overrides. Template never propagates to
  siblings automatically. Default restore target is the same character only;
  copying between characters is outside increment1, not an implicit fallback.
- Envelope: schema version, section schema versions, producer build/flavor,
  server-issued immutable snapshot id/revision, server time, section byte lengths
  and content digests, explicit identity/scope. Bound aggregate sizes and counts
  before allocation, validate finite/ranged values, reject unknown incompatible
  schema; reject unsupported sections rather than silently dropping them.
- Typed allowlist, not a blacklist: macro names/recognized game command lines;
  portable chat/UI/camera preferences; validated action IDs/book-set references;
  normalized layout anchors/size plus source viewport. Preserve original layout
  and preview screen-fit changes; do not permanently rewrite it on smaller devices.
- Never export auth/login/token/social credentials, server endpoints, named servers,
  plugin/script code, logs/chat history, machine paths, display-device IDs,
  launcher channels, game/install directories or unknown config maps. Performance/
  display mode and device bindings stay device-local in increment1. Unknown addon
  commands/path-bearing macros excluded pending explicit safe typed support.
  Free-form macro text could contain user-entered secrets: no automatic upload;
  preview content locally, reject unsupported commands, no payload logging, and
  require deliberate selection. No regex can promise to identify every secret.
- Restored macros are inert data: never execute on import. Gameplay/autonav state,
  active scripts, account privileges, equipment, inventory, balances and progression
  are not settings and cannot be restored by this feature.

Explicit flows and conflict protection
1. Save to server: select sections/scope, review contents/exclusions locally, then
   confirm. Create immutable new snapshot using expected latest revision (CAS).
   Concurrent update produces conflict and new preview, never last-writer-wins.
   Stable request id makes retries idempotent, response loss cannot create copies.
   Retain previous server revisions; no silent pruning/deletion in increment1.
2. Restore: select snapshot, download to bounded memory/staging, validate digest,
   schema, identity and section adapters, show before/after counts and changed
   preferences/positions. Cancel makes no changes. Confirmation binds exact
   snapshot+section selection+local revision+server revision+session identity.
3. Recheck identity and local edits at apply; account switch/relog/disconnect or
   any changed revision invalidates preview. Require idle settings editor, no macro
   execution or zone/cutscene transition. No forced logout/restart or player input.
4. Before any write, durably save ALL affected local preimages and a recoverable
   transaction journal. Stage validated bytes, atomically replace each file under
   one settings writer, commit journal last; recover/rollback partial writes after
   interruption. Disk-full, preimage failure or stale revisions => no apply.
   Preserve unrelated keys and files byte-for-byte where possible. UI mode changes
   retain existing timed Keep/Revert; config save loop must honor restore lock.
5. Undo restore uses retained preimage as another previewed restore, with the same
   current-revision guard, not a silent overwrite of subsequent edits. Server save
   and local restore are separate explicit actions; restoring never overwrites the
   server snapshot. No file paths or archive entries supplied by server payload.
