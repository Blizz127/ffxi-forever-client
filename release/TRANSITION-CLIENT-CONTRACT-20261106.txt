1. Reconcile the original T1 hypothesis
--------------------------------------
session.rs::event_end queues complete_eventend output after onEventFinish and
apply_script_pos. However, the datagram handler calls process_zone_request before
reply construction. For an accepted cross-zone destination, that method clears
self.pending and replaces it with the 0x00B alone. Therefore inspecting event_end
in isolation is insufficient: current source does NOT send that queued 0x052 in
the old-zone reply. Closed/missing endpoint and script-error paths differ and must
be traced separately. This does not prove the installed server matches this source.
Also, client mode 1 is an update acknowledgement, not inherently a control release.

2. Client lifecycle and readiness
--------------------------------
client/mod.rs::NetEvent::Zoning arms zonefade immediately, even when ZoneIn is in
the same event drain. ZoneIn discards old pending/live events, resets screen,
controls and autorun, then holds black and queues the login event carried by 0x00A.
Do not require a separate 0x032/034 for an owed opening scene.

client/event.rs::can_prepare_event allows CPU script preparation and actor requests
while GPU streaming continues. zone_ready requires matching installed CPU/GPU
resources, settled state and no zoning_since. SendResRdy shares the resource gate,
but MUST NOT wait for actors: the acknowledgement may prompt those actor packets.
VM begin additionally requires bound actors/models. begin sets control_lock.
Screen/script fade and zonefade are separate; resource ACK or actors-ready alone
does not establish the first displayed scene frame or restoration of input.

client/event.rs::release / event_vm.rs::Runtime::release:
- mode 0 clears control_lock and marks a running event released/cancellable;
- mode 1 clears VM wait_update; mode 3 clears VM input_wait;
- mode 2 cancels only a matching running VM event;
- when no VM exists, modes 1/2/3 clear control_lock without clearing event_pending;
- mode 4 clears the fishing latch only.
This pre-VM behavior needs a deterministic packet-order regression. It is not proof
of the owner's native symptom. Platform reports no current Forever mode-2 sender.

Missing/malformed DAT currently reaches the no-script fallback after resource-ready:
release black, send FINISH option 0/mode 0, clear lock. Idle VM timeout uses cancel
0x40000000. Neither is a no-completion abort: server onEventFinish may alter state
even for cancel, and option 0 may select the first choice. Do not change/replay this
against a real character or call replacement of option 0 intrinsically safe.

--------------------------------------------------------

existing authorized fixture identifier. Use monotonic times within each process;
retain UTC anchors and packet sequence/direction for cross-process correlation.
Never subtract unsynchronized wall clocks to claim latency. Metadata only; exclude
credentials, chat text, event parameter contents and owner character state.

Stages, each with event/zone and session-generation identity where available:
 A client FINISH enqueue AND actual c2s 0x05B send

 E destination login, s2c 0x00A receive/dispatch including owed-event identity

 G event queued / DAT prepared / CHARREQ sent / actor replies / actors ready

Existing logs cover zone-in, resource ACK enqueue, GPU-ready, event queued/prepared,
actor request/ready, and release dispatch. 'actors ready' is inside begin before
Runtime construction; it is NOT a first-frame timestamp. The existing allowlisted
extract-stages.py must leave absent stages UNKNOWN. It cannot prove wire send,
generation, control ownership or rendered frame state from these lines alone.
Do not dump raw event-start log lines into reports: those include params.

Compare matched before/after fixture, cache state and rendering setup. Report actual
stage durations and stalls, not a nominal 400 ms datagram estimate or simulated
script-frame count as wall-clock time. Missing instrumentation/capture is a gap.
